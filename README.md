# Draft

Draft is an experiment in one idea: if coding models become good at writing and
maintaining software, perhaps we can rely less on layers created mainly to make
programming manageable for humans, and write more direct, lower-level software
again.

The language design grew from conversations with LLMs. Coding agents then built
the bootstrap compiler, core library, examples and a Turbo-style terminal IDE
under human architectural direction. This repository is the result: not a
production language, but something concrete enough to test the idea with real
programs.

Draft is heavily inspired by [Odin](https://odin-lang.org/), with explicit
memory, compile-time parametrics and structural inspection, native
interoperation, optional typed synthesis, and a compiler designed around
deterministic parallel work.

## A word from the author

*The debt to Odin should be said clearly. Ginger Bill and the Odin contributors
built a real language through years of serious work. Draft is not a replacement
or a competitor.*

*Casey Muratori's [work](https://caseymuratori.com/)—from Handmade Hero to his
uncompromising arguments against accepted complexity—was another influence.
The agent rules owe much to that spirit.*

*There is an even bigger debt to Jonathan Blow and Jai: in particular, the idea
of building a language together with the programs and tools one actually wants
to build, rather than designing it only in the abstract. What he is doing is
artisan work in the true sense, and “amateur” work in the oldest and best sense
of that word: work moved by love and care for the craft. I think there is
something very deep in that.*

*Draft is not comparable to any of this work. It is an experiment, a study, an
evaluation of sorts, made as a side project over a few days. Apart from
architectural guidance and occasional decisions, I did not follow most of the
implementation closely; I mostly kept coding agents working and reacted to
what they built. The whole repository was generated by Codex under my
direction. The agents were pushed toward simple code and a fast, inspectable,
parallel compiler—and asked to refactor foundations when real examples exposed
bad choices. This does not mean the ideal was achieved. That is part of what is
being evaluated.*

*I have only tested Draft myself briefly, on an Apple Silicon Mac, and had some
fun trying the examples. I have not personally tested Linux or Windows. The
coding agents claim those targets work and built GitHub Actions to exercise the
claims on macOS ARM64, Linux ARM64, Linux x86-64 and Windows x86-64. Useful
evidence, yes; the same as people really using it, no.*

[Draft 0.1.0-alpha.4](https://github.com/miguelbranco80/draft/releases/tag/v0.1.0-alpha.4)

archive](https://github.com/miguelbranco80/draft/releases/download/v0.1.0-alpha.4/draft-0.1.0-alpha.4-aarch64-macos.tar.xz):

```sh
  https://github.com/miguelbranco80/draft.git draft-source
tar -xf draft-0.1.0-alpha.4-aarch64-macos.tar.xz

  draft-source/examples/language-tour
draft-0.1.0-alpha.4-aarch64-macos/bin/draftc run \
  draft-source/examples/tetris -O2
```

## A little code

The ordinary side should feel familiar to an Odin programmer:

```draft
package app

import core/console

sum :: proc(values: []i64) -> i64 {
    total: i64
    for value in values {
        total += value
    }
    return total
}

main :: proc() {
    values := [5]i64{2, 3, 5, 7, 11}
    assert(console.println("sum:", sum(values[:])) == .none)
}
```

Type and value parameters are explicit, use a small closed set of constraints,
and become ordinary fixed native code:

```draft
Buffer[T: type, N: usize] :: struct {
    values: [N]T,
}

sum[T: number] :: proc(values: []T) -> T {
    total: T
    for value in values {
        total += value
    }
    return total
}
```

Static argument packs keep every exact type. The loop and `when` happen at
compile time; there is no runtime `any`, RTTI, or C varargs object here:

```draft
sum_mixed :: proc(values: ..type) -> i128 {
    total: i128
    for value in values {
        when type_kind(type_of(value)) == .signed_integer {
            total += cast[i128](value)
        } else when type_kind(type_of(value)) == .unsigned_integer {
            total += cast[i128](value)
        } else {
            static_assert(false, "sum_mixed accepts only integers")
        }
    }
    return total
}
```

## The shape of the language

Draft deliberately keeps much of Odin's low-level, procedural character. The
larger differences and additions are:

- Packages are private by default and resolve from one canonical workspace.
  There is no registry or dependency solver: download source and keep it with
  the program. This is vendoring in the plain sense: copy dependency source
  into the workspace and version it with the program.
- The exact version of `core` is embedded byte-for-byte in `draftc`. Imported
  core and library packages are checked with the program, while native emission
  includes only code reachable from the selected artifact.
- Parametrics use explicit type/value parameters, closed constraints and
  modest inference. Structural type inspection, static packs and `when`
  refinement remain compile-time and produce fixed signatures.
- The language has structs, tuples, enums, variants, unsafe unions, distinct
  types, pointers, arrays, slices, endian scalars, SIMD, packed fields and bit
  fields. Layout can itself be inspected at compile time.
- C interoperation includes imports, exports, callbacks, C variadics, generated
  headers, static/dynamic libraries and package assembly.
- Draft has no methods, traits, exceptions, closures, operator overloading,
  implicit moves/destructors, runtime `any`, or AST macro system. Growable
  arrays, maps, `Option` and `Result` are ordinary core-library types.
- The current target profiles are Apple Silicon macOS, AArch64 Linux, x86-64
  Linux and x86-64 Windows. The core library already supports real programs,
  including Tetris, editors, a terminal UI and raylib Asteroids.

### The more radical experiments

Then there are `docs`, `deny`, `judge` and `...`. These are deliberately
optional, stranger ideas. `docs` carries design context as part of the program;
`deny` makes a restriction such as “no allocation, assembly or unchecked
access” transitive through everything a region can call; `judge` asks an agent
to review a claim at one exact typed program point; and `...` asks an agent to
write source for one exact grammar and type-shaped hole. A judgment is evidence,
not proof.

That permits things like this:

```draft
package protocol

docs "The packet layout and decoder contract."
    file "PROTOCOL.md"

import core/heap

Packet :: struct {
    ... "Declare the wire fields described in PROTOCOL.md."
}

decode :: proc(input: []u8) -> Packet {
    deny heap, asm, unchecked, context.allocator {
        judge "Every input offset used below is checked against len(input)."
        return ... "Decode one Packet without allocating."
    }
}
```

Yes: Codex may generate the fields of a type and the body of its decoder, while
the compiler checks the result as ordinary Draft source, including the return
type and the transitive denials around it. A synthesis hole can also stand for
package declarations, statements or even one assembly instruction.

In the current bootstrap, fresh `...` resolution and `judge` runs use the Codex
CLI, so those commands need Codex installed and authenticated. `docs`, `deny`
and ordinary handwritten Draft do not. Accepted generated source is pinned;
normal builds never call Codex. Is all of this sane? Maybe not. It is a fun
exploration of what happens when the coding agent becomes an explicit part of
the language while the compiler still sets the hard boundaries.

See the [language tour](examples/language-tour/package.draft), [examples by
feature](examples/README.md), and [specification](docs/README.md) for the less
friendly details and current limitations.

## The compiler experiment

The compiler is trying to be fast by construction, not by depending on a
persistent cache. One command owns one semantic work graph: discovery is eager,
completion is demand-driven, independent work runs in parallel, and publication
stays deterministic. After profiling the larger examples, the coding agents
followed architectural guidance to replace several early broad passes with that
demand-driven graph and parallel ready sets. The present bootstrap emits through
LLVM in process, avoids unreachable native code, and uses package-level ThinLTO
at O2.

On the qualification Mac:

- An O2 hello-world build measured 84 ms.
- Three fresh O0 DraftIDE builds measured 209–213 ms. That build checked 463
  runtime procedures across 26 packages—including imported core and library
  source—and emitted 398 reachable procedures.

These are dated observations from one machine, not performance promises. The
actual design and measurements live in the [semantic work
graph](docs/implementation/semantic-work-graph.md) and [native
qualification](docs/releases/native-host-qualification.md) documents.

## DraftIDE

DraftIDE is a mostly-Draft terminal IDE inspired by the old blue Turbo
Pascal/C environments. It works over SSH and combines a real editor, semantic
navigation and Build/Run with the compiler in process; it is also a useful
stress test for the language and its small reusable terminal UI.

## Contributing

Clone the repository only if you want to change the language, compiler, core
library or tools, or build the distribution itself. Read
[`AGENTS.md`](AGENTS.md) before making changes. If a coding agent is doing the
work, give it this brief:

> Read `AGENTS.md` and the relevant specification first. Implement this change
> through the compiler, tests and owning documentation, and keep the work in
> small coherent commits.

On Apple Silicon macOS, build and test the bootstrap with:

```sh
brew install cmake llvm@22
git clone https://github.com/miguelbranco80/draft.git
cd draft
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release \
  -DLLVM_DIR="$(brew --prefix llvm@22)/lib/cmake/llvm"
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Linux, Windows, installation and packaging instructions are in [Building and
releasing Draft](docs/operations/releases.md).

## Roadmap

Draft itself probably has little future; rerunning the experiment with better
models may matter more than maintaining this implementation. If it continues,
the interesting directions are:

- **Self-host the compiler.** The bootstrap is C++; the intended second compiler
  is Draft written in Draft. That is the strongest test of whether the language
  and core library are actually coherent.
- **Try GPU compute, because why not.** Modern machines are heterogeneous, yet
  GPU programming is often treated as a separate language and tooling world. A
  small [`gpu proc`](docs/specification/07-future-ideas.md#gpu-procedures)
  boundary could make address spaces, execution rules and lowering explicit
  while devices, queues, buffers, transfers and dispatch stay ordinary library
  code. Start with compute; shaders can follow if the model holds. No hidden
  transfer or giant runtime is the point.
- **Go lower.** Freestanding and embedded targets would test whether the same
  direct language can keep shedding hosted assumptions instead of accumulating
  them.
